# Progress — August 5, 2026: Realtime DLO Tracking

Status after this session's additions. The capability in one sentence:
**point an Azure Kinect at an open cable, run one command, and get tracked 3D
keypoints — no masks, no robot, no clicks, no prompts.**

```bash
python dlo_tracking_live.py --source kinect
```

---

## 1. The full pipeline, stage by stage

**Stage 1 — Camera** ([frame_source.py](frame_source.py)).
`KinectSource` starts the camera (720p color, NFOV depth, 30 fps). A capture
thread converts each capture to the chunk format: BGR color, uint16 depth in
mm registered to the color frame, K from the device calibration, undistorted
with `newCameraMatrix = K`. The thread keeps only the newest frame — when the
consumer is slow, old frames drop, they never queue.

**Stage 2 — Automatic start** ([bootstrap.py](bootstrap.py)).
For each incoming frame, until one passes:

1. A promptless candidate mask: the Frangi ridge filter finds thin, long
   structures inside the workspace depth gate (`--z_range`), or background
   subtraction (`--bootstrap bgsub`) finds "the thing that was not there
   before".
2. The acceptance test: the candidate's skeleton must be one open curve —
   enough pixels, two real endpoints, one path that covers most of the
   skeleton. Fail → drop the frame, try the next.
3. The accepted path's interior points prompt SAM2. SAM2 grows the partial
   candidate to the full cable; refine rounds re-prompt from SAM2's own
   skeleton while the path keeps growing.
4. The two farthest endpoints of the final skeleton, back-projected through
   the depth (walking inward past depth holes), become the EE pair.
   Measured on the recorded data: 22 mm and 11 mm from the true robot
   gripper positions.

**Stage 3 — Tracker init.**
One `WireTracker` is built with the same parameters as the offline driver and
the one-frame EE array. It snaps the two 3D ends to the mask skeleton, finds
the path between them, and spaces the 15 keypoints along it. Verified: init
geometry equal to the offline robot-EE init within 1 mm of total path length
(1033.5 mm vs 1034.7 mm).

**Stage 4 — The tracking loop.**
Per frame: newest camera frame → live mask (SAM2 from its internal memory,
no prompt — or the point-cloud-difference segmenter with `--segmenter
pcdiff`, see §4) → mask inverted into `precomputed_arm_mask` (the same
convention as the offline driver) → `process_frame` → keypoints. The display window shows
the keypoints, edges, and fps. From here on the tracker needs no external
help: it finds the cable ends itself from each frame's skeleton tips
([wire_tracker.py:1032-1044](../tracker/wire_tracker.py#L1032-L1044)).

**Stage 5 — Self-recovery.**
On every frame the tracker skips, the driver recomputes the cable ends from
the current mask and refreshes the stored EE pair. So when the tracker decides
to warm-restart, it re-initializes with the ends of NOW, not of frame 0.

**Stage 6 — Outputs.**
On exit: `3d_keypoints.npz` (same keys as the offline output). With
`--record`: the whole session in the exact chunk format, so the unchanged
offline [dlo_tracking.py](../dlo_tracking.py) can evaluate a live session
afterwards.

Replay mode runs the same driver against the shipped chunks with
**bit-identical parity** to the offline driver — the regression test for every
future change.

## 3. Still missing before live camera tracking works

1. **The loop will not hold 30 fps as written (SAM2 path).** SAM2 runs
   synchronously: ~30 ms + 11–21 ms tracker ≈ 20–25 fps. Frames drop cleanly,
   so tracking stays correct at a lower rate. The fix is SAM2 in its own
   thread with a one-frame mask lag
   ([REALTIME_SAM2_OVERVIEW.md §2.2](../REALTIME_SAM2_OVERVIEW.md))
   — not implemented yet. A **CUDA GPU on the live machine is required**;
   SAM2 on CPU is ~10× too slow. `--segmenter pcdiff` (§4) sidesteps both:
   ~3 ms/frame on CPU, no GPU needed — at the price of the static-reference
   limitations documented there.
2. **`--z_range` must be set for the rig.** The acceptance test verifies
   "one open thin curve"; the workspace depth gate is what separates the
   cable from other thin structures (window frames, tent edges). The default
   (500–2000 mm) is a guess, not the rig.
3. **Scene conditions at start.** Auto init needs the cable open and
   uncrossed for at least one frame. `bgsub` needs the empty-scene ritual
   first. Fallback: `--init click`.
4. **Raw output, no consumer.** Live keypoints are raw (the offline Gaussian
   smoothing is non-causal, correctly not applied) and written to disk only
   at exit. A live publish step (ZMQ/ROS topic, or a causal EMA filter) does
   not exist yet.
5. **Scope: DLO only.** The BDLO needs the per-frame EE pair (markers on the
   grippers, or the robot stream) plus its documented speed work; cloth and
   fabric need their timing measured first.

**Order of attack when the camera arrives:** hardware smoke test (1) → set
`--z_range`, run a real session end to end (4, 5) → SAM2 thread (2) and
watchdog (3) once the basics hold.

## 4. Added this session: the point-cloud-difference segmenter (`--segmenter pcdiff`)

An alternative to SAM2 for the per-frame live mask, using the deformable_seg
segmentation method. New file [pcdiff_segmenter.py](pcdiff_segmenter.py).

```bash
python dlo_tracking_live.py --source kinect --segmenter pcdiff
```

**How it works.** At start-up, record the empty scene for `--bg_frames`
frames and store its median depth as the reference. Then, per frame: a pixel
is foreground when its 3D point sits more than `--pcdiff_threshold` mm
(default 30) from the reference point — i.e. "the cable is what wasn't there
before". Same cleanup as SAM2 masks (close + largest component). This is the
per-frame math of `deformable_seg/seg_with_arms_utils.py`; only the
reference differs — offline it is a second, synchronized arm-only recording
of the same robot trajectory, which doesn't exist live, so a static
empty-scene reference stands in.

**Speed.** Both point clouds come from the same pixel grid, so the 3D
distance reduces exactly to `|Δdepth| ·‖ray‖` with the ray norms precomputed
once. Result: **~3 ms/frame on CPU** (SAM2: ~30 ms on GPU). No torch, no GPU.

**Driver integration.** Purely a mask-source swap — the tracker takes any
binary mask. In `--init auto`, the pcdiff mask itself is the frame-0
candidate (same acceptance test, same EE-endpoint extraction, no SAM2
prompting); in `--init click`, clicks give only the EE pair. Everything else
(EE refresh on skips, `--record`, display) is unchanged.

**Verified (synthetic, no camera):** exact match with the full 3D norm;
recall 1.000 / zero false positives on a synthetic cable over a noisy table;
end-to-end driver run with a stubbed Kinect: 50/50 frames tracked at 36 fps.
Replay parity path still passes.

**Limitations (why SAM2 stays the default).**
- The reference is static: a robot arm that enters the workspace after
  capture becomes foreground. Keep the arms outside the `--z_range` gate.
  Handling an arm manipulating the cable inside the gate would need the
  offline method's synchronized arm-only replay, or an arm mask rendered
  from robot kinematics — neither is implemented.
- An object lying flatter than `--pcdiff_threshold` on the table is
  invisible to the diff.
- The empty-scene capture is needed at every session start, and the
  reference is not refreshed if the camera or scene shifts mid-session.
